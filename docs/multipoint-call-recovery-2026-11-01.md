# 通话切回电脑后的控制链路恢复

日期：2026-11-01（Asia/Shanghai）。源码：2.0.4 本地候选版本。
本轮只修复、编译和测试，按用户要求不重新生成安装器或 ZIP，也没有上传 GitHub。

## 对原排查结论的判断

“音频已恢复，但控制请求仍然超时”的排查方向合理。当前实现的音频播放和
SPP/RFCOMM 控制不是同一条链路；系统报告蓝牙连接存在，不能证明控制请求能完成。
不过，错误消息本身不能证明真实通话期间 Windows socket 的具体状态。
本轮验证的是软件在这种故障状态下的检测与恢复，不代表已经复现真实手机通话。

当前源码保留了之前的修复：ACK 等待超时立即使会话失效、查询响应连续两次
超时使会话失效、取消挂起 I/O、重连前关闭旧传输、V2 初始化失败向上传递。
但原实现还会在收到任意可解码帧时清零查询超时次数，包括 ACK 和无关通知。

因此仍存在以下遗漏：

```text
查询 1 -> 收到 ACK -> 响应超时，计数 1
查询 2 -> 收到 ACK -> 计数被清零 -> 响应超时，计数又变成 1
重复查询 -> 一直显示连接正常，服务层不会重连
```

无关通知也会产生相同效果。只有完全静默的模拟设备会稳定触发旧的保护，
所以之前“无 ACK、无响应”的测试通过，并不足以排除这个问题。

## 最小复现与修改

在修改生产代码前增加会话层测试。只回 ACK、只发无关通知、两者都存在但没有
匹配响应时，第二次查询超时之后 `session.isConnected()` 仍为 `true`。
两个新增测试的六个分支均出现断言失败，确认检测缺口存在。

`SonyProtocolSession` 现在只在 `sendAndAwaitResponse()` 成功取得匹配响应后
清零查询超时次数。ACK、无关通知、被响应过滤器拒绝的帧，以及成功的 ACK-only
写命令，都不能清除查询失败记录。

- 单次查询响应超时仍保留连接，允许孤立的可选查询失败。
- 连续两次查询响应超时，即使底层传输仍报告 connected，也使会话失效。
- ACK 等待超时立即使会话失效的原有行为保留。
- 收到匹配响应后立即断开传输的设备管理命令，仍可向调用方返回该响应。
- 服务层随后关闭旧控制连接，并只重连持久化选择的目标地址。
- 不自动重放失败的关机命令；恢复连接后由用户重新发起操作。

这是请求完成情况的健康判断，没有新增电话状态侦测。恢复时间取决于维护节拍、
请求超时和已有重试退避，不能保证挂断瞬间恢复。

## 回归覆盖

测试均使用模拟传输，不向真实耳机发送写命令。

| 层级 | 验证内容 |
| --- | --- |
| 协议会话 | 完全静默、只回 ACK、只发通知、ACK 加通知；匹配响应恢复计数；ACK-only 写入与过滤失败不能掩盖故障 |
| 设备服务 | 通过真实维护步骤触发两次查询超时；底层连接保持 connected；失效期间阻止写入；关闭旧会话后重连同一地址 |
| 目标绑定 | 另一台 Sony 耳机也在候选列表中且系统已连接，恢复时仍不切换目标 |
| 恢复后的功能 | 电量、降噪、EQ、DSEE、多点查询状态恢复 valid 且清除错误；真实 JSON 处理器接受 ANC 和关机 |
| 原生 Qt | 运行生产 main/QML/controller/backend，界面从已连接变为 retrying，再自动恢复；随后实际托盘控制及关机测试通过 |
| V1 兼容 | 修正共用模拟器遗漏的 V1 电量响应与降噪布局，保留 V1 生命周期、协议代际和禁止误发关机 opcode 的检查 |

对应依据和更新后的模拟界面截图见[界面术语](ui-wording.md)。

## 真机验收与产物边界

仍需在真实电脑、手机和耳机上按以下流程确认：

1. 记录耳机型号/固件、Windows 版本与蓝牙适配器，电脑和手机同时连接耳机。
2. 在电脑播放音频，手机接听并结束通话，等待声音返回电脑。
3. 观察界面是否从控制超时自动进入重连，并恢复所选耳机。
4. 确认电量及各功能查询恢复；经使用者确认后，验证降噪和关机操作。
5. 同时存在另一台配对耳机时，确认恢复始终针对原设备。

本轮没有进行以上真实通话及写命令验收。
既有 `SonyDeviceCenter-Qt2-2.0.4-dev-Setup.exe` 和
`sony-device-center-2.0.4-dev-win64.zip` 的 SHA-256 未改变，
因此它们不包含本轮补充修复及名称更新。用户要求暂不重新打包。
